# Model catalog path

How versioned catalog requests are answered: the front-door intersection, the `apisix-models` catalog leg and the operator models table.

## Front-door model catalog intersection

Parameterized Codex catalog requests (`GET /v1/models?client_version=...`) are answered by the **front** APISIX via `lua/model_list_intersection.lua` (route `ai-api-models-intersect`, priority 200): it serially fetches (1) Sub2API's own response with the client's key and original query — the slug set of that response is the group's entitlement (mapping union ∩ group models list; its hardcoded metadata is discarded) — and (2) the enriched live manifest from `apisix-models` (see below), then returns the intersection with metadata taken from model-catalog. Sub2API errors pass through verbatim (implicit auth); if the enriched leg cannot supply a valid catalog, the front door returns 502 instead of using Sub2API template metadata. A catalog composed by model-catalog from eligible cached source responses remains a valid enriched-leg result; user authorization is still fetched for each request. Only the model-catalog-to-CPA native catalog version is pinned to `1`: this avoids CPA's legacy-client reasoning-level filter without bypassing authentication or membership admission. Other upstream inventory requests retain the caller's version (the table retains its existing inventory version `v0.65.0`); the table's version caption reports the CPA catalog version. Declared reasoning levels do not prove account/channel inference capability.

## Catalog leg and models table

The intersection's catalog leg is a plain `GET /v1/models` (with the caller's `client_version`) from the front door to `apisix-models:9080` over the two-member internal `front-catalog` network. It carries no client credential: the codex-models route needs none, and model-catalog holds its own CPA key. `apisix-models` routes only `/v1/models` to `model-catalog`; it has no models-table route.

The front door's second listener (`9083`) serves the operator models table. `apisix-host-netns` publishes it on `127.0.0.1:9083` and `${TAILSCALE_IP}:9083` through `apisix-host-table-relay`. Localhost and Tailscale are the trusted operator domain, so there is no source-address filter. The routes `models-table` (`GET /models-table`) and `models-table-refresh` (`POST /models-table/refresh`) match only `server_port == 9083` and proxy to `model-catalog:8090` over the two-member `front-model-table` network; the public listener (`9080`) returns the opaque 404 for both. The 9083 listener also answers the ordinary public API routes, scoped to the same trusted domain.

`GET /models-table` is model-catalog's server-rendered diagnostic page and `POST /models-table/refresh` performs an explicit full-chain diagnostic refresh. The table has eleven columns, including separate `input_modalities` and `output_modalities`, and adjacent independent `max_tokens(abandon)`, `max_completion_tokens`, `max_output_tokens` columns. `abandon` marks only the deprecated Chat Completions request parameter, not an invalid catalog property. The complete table and refresh form arrive as HTML with no page JavaScript or browser JSON request. Startup, scheduled refresh (default `30m`), eligible entry refresh and the button share one bounded full-chain job. `GET /models-table` returns the most recently published table immediately; if the last successful completion is older than the entry window (default `10m`), or none exists, it starts or joins collection in the background. A cold page immediately shows loading/no-data rather than waiting for upstreams. The form's `POST /models-table/refresh` starts or joins that job and waits for its result. YAML keys `scheduled_refresh_interval` and `entry_refresh_window` independently accept positive durations; the entry window may exceed the scheduled interval. Pages show the last successful completion and next scheduled tick. Failures and retained-input fallbacks do not advance the success window. The job bypasses freshness for model-catalog's CPA/AISIX, channel-inventory, metadata-source and projection caches, rebuilding from the current CPA snapshot. Metadata failures use eligible last-successful input responses with a warning; a manual refresh without CPA authority returns an error page. A failed background attempt retains the previous diagnostic table with a warning, not as fresh authority for JSON catalogs. Shutdown cancels the schedule and active work. See [scheduled refresh](models-table-scheduled-refresh.md). Column values do not establish request budgets or protocol support. Missing fields display `未知`; explicit `null`, `false`, `0`, `""`, arrays and objects are rendered as text without fallback or HTML execution.

Ops notes:

- Unparameterized `/v1/models` (missing or empty `client_version`) and `/models` on the **front** door use `model_list_intersection.list()` (route `ai-api-models-get`). The handler fetches Sub2API with the caller's path, query and credentials, then orders bare IDs (no `/`) first and all others second, each in case-sensitive Unicode code-point order; equal IDs keep their relative order. Members, record JSON bytes and other top-level fields stay unchanged. Non-2xx responses pass through with their status and body; unrecognized 2xx bodies also pass through unchanged with a WARN. Upstream ETag and Cache-Control are dropped. Recognized lists get `Cache-Control: private, no-cache`, a strong ETag of the final body, `Vary: Authorization` (merged with upstream Vary) and `304`/`412` conditionals, as on the intersection. The handler shares its one-request admission slot and 64 MiB response limit. On **apisix-models** every `GET /v1/models` goes to model-catalog, which returns the standard `{object:"list", data:[{id}]}` list when `client_version` is missing or empty.
- The Sub2API "sync models" button failing for CPA accounts is known-harmless: catalog data comes from model-catalog, not from Sub2API's sync.
- Never write model metadata into Sub2API's DB (e.g. `extra.upstream_model_metadata` snapshots) — they go stale by construction; the intersection makes them unnecessary.
- Enriched-inventory membership is decided by model-catalog's [membership script](model-catalog.md#membership-script) `catalog.lua`; the default keeps CPA IDs under a CPA prefix, its `EXTRA_CPA` matches, every AISIX ID and `static_models`. The bare copies CPA lists under its default `force-model-prefix: false` are not members.
- Catalog visibility is the intersection of the enriched inventory, the group's configured models list, and Sub2API's account model-mapping union. Adding a group entry alone does not make an unmapped model visible. Listing a model is not proof that an inference request succeeds.
- Change account/group configuration through the supported admin API/UI while preserving unrelated settings; verify the served catalog afterward. Do not assume every credentials field is merged by a partial PUT, and do not diagnose stale cache or restart services merely because a model is absent. Follow the [coupled-service operations policy](operations.md#operations) if a restart is separately required.
- Troubleshoot catalog metadata via `http://127.0.0.1:9083/models-table` (or the Tailscale bind): missing capability cells show `未知`, while explicit nulls show `null`; model-catalog WARN logs name the failing channel `prefix`. The page's `POST /models-table/refresh` button bypasses model-catalog's normal five-minute snapshot/read/projection caches, but it does **not** run or control the independent `cpa-model-sync` service, whose production interval is ten minutes. CPA must already have loaded a provider before the refresh can observe it.
- The front intersection validates identities and keeps selected records' original JSON fragments, avoiding Lua floating-point re-encoding of unknown numbers. Duplicate routing keys/collections fail closed. All external `/v1/models` and `/models` requests share one APISIX-wide admission slot across workers and callers; excess requests wait briefly, then receive bounded `503` instead of running concurrently. Entitlement-first ordering, final-entity ETags and 64 MiB limits remain in place; caching is confined to model-catalog's upstream reads.
- Outbound pool slots remain held until response bodies close. Native/API-call, management inventory and bulk-source responses keep their respective 64/8/16 MiB limits; exceeding a limit is an error, not silent truncation.
- Independent output-token fields and three-column display: [local verification and compatibility](records/output-token-field-semantics-verification.md), [2026-09-08 production deployment](records/output-token-field-deployment-2026-09-08.md). The subsequent [five-channel source configuration deployment](records/source-chain-deployment-2026-09-08.md) records the current 78 output-field / 22 input-limit coverage snapshot.
- Pure server-rendered page implementation, browser-without-JS checks and deployment limits: [SSR verification](records/models-table-ssr-verification.md), [2026-09-08 production cutover](records/models-table-ssr-deployment-2026-09-08.md).
- Reproducible local checks and the 45-scenario evidence map: [layered metadata verification](records/layered-metadata-verification.md). This is implementation/fixture evidence, not a production deployment or inference claim.
- model-catalog needs no egress policy: source data is bundled at build time, and channel-native endpoints (e.g. ollama.com `POST /api/show`) are reached by CPA through `api-call`, so CPA's egress policy must allow them; a denied read degrades that channel to a WARN, never a catalog failure.
- `/models-table` also lists models hidden by `include_models` with the deciding rule, and models kept only because another model references them (`inherit`/`metadata_from`); hidden, unreferenced models are not processed.
