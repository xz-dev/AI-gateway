# Model catalog path

How versioned catalog requests are answered: front-door intersection, model-catalog-sidecar and the models table.

## Front-door model catalog intersection (model-catalog-sidecar)

Parameterized Codex catalog requests (`GET /v1/models?client_version=...`) are answered by the **front** APISIX via `lua/model_list_intersection.lua` (route `ai-api-models-intersect`, priority 200): it serially fetches (1) Sub2API's own response with the client's key and original query — the slug set of that response is the group's entitlement (mapping union ∩ group models list; its hardcoded metadata is discarded) — and (2) the enriched live manifest through `model-catalog-sidecar`, then returns the intersection with metadata taken from the enricher. Sub2API errors pass through verbatim (implicit auth); if the enriched leg cannot supply a valid catalog, the front door returns 502 instead of using Sub2API template metadata. A catalog composed by the enricher from eligible cached source responses remains a valid enriched-leg result; user authorization is still fetched for each request. Only the enricher-to-CPA native catalog version is pinned to `1`: this avoids CPA's legacy-client reasoning-level filter without bypassing authentication or membership admission. Other upstream inventory requests retain the caller's version (the table retains its existing inventory version `v0.65.0`); the table's version caption reports the CPA catalog version. Declared reasoning levels do not prove account/channel inference capability.

`model-catalog-sidecar` (nginx-unprivileged, read-only, non-root) is a narrow catalog bridge: `GET /v1/models` forwards to `apisix-models` with no credential attached (the codex-models route requires none; the enricher holds its own CPA key), `GET /models-table` proxies to the enricher's server-rendered diagnostic page, and `POST /models-table/refresh` performs an explicit full-chain diagnostic refresh. The table has eleven columns, including separate `input_modalities` and `output_modalities`, and adjacent independent `max_tokens(abandon)`, `max_completion_tokens`, `max_output_tokens` columns. `abandon` marks only the deprecated Chat Completions request parameter, not an invalid catalog property. The complete table and refresh form arrive as HTML with no page JavaScript or browser JSON request. Startup, scheduled refresh (default `30m`), eligible entry refresh and the button share one bounded full-chain job. `GET /models-table` returns the most recently published table immediately; if the last successful completion is older than the entry window (default `10m`), or none exists, it starts or joins collection in the background. A cold page immediately shows loading/no-data rather than waiting for upstreams. The form's `POST /models-table/refresh` starts or joins that job and waits for its result. YAML keys `scheduled_refresh_interval` and `entry_refresh_window` independently accept positive Go durations; the entry window may exceed the scheduled interval. Pages show the last successful completion and next scheduled tick. Failures and retained-input fallbacks do not advance the success window. The job bypasses freshness for the enricher's CPA/AISIX, channel-inventory, metadata-source and projection caches, rebuilding from the current CPA snapshot. Metadata failures use eligible last-successful input responses with a warning; a manual refresh without CPA authority returns an error page. A failed background attempt retains the previous diagnostic table with a warning, not as fresh authority for JSON catalogs. Shutdown cancels the schedule and active work. See [refresh verification and rollout handoff](models-table-scheduled-refresh.md). Column values do not establish request budgets or protocol support. Missing fields display `未知`; explicit `null`, `false`, `0`, `""`, arrays and objects are rendered as text without fallback or HTML execution. Everything else gets 444. The sidecar joins both `apisix-catalog-source` (front side) and `apisix-catalog-target` (apisix-models side) /29 nets, same one-way shape as the socat relays. Both models-table paths are published only on Tailscale and localhost via `models-table-host-netns` + `models-table-relay` (`<tailscale-ip>:9083` / `127.0.0.1:9083`) — containers attached solely to `internal` networks cannot publish ports directly, so the netns-owner + socat pattern carries the exposure.

Ops notes:

- Unparameterized `/v1/models` on the **front** door keeps going straight to Sub2API (route `ai-api-models-get`), but shares the same global one-request admission slot as versioned catalog requests; on **apisix-models** it goes directly to CPA, as does an empty `client_version`.
- The Sub2API "sync models" button failing for CPA accounts is known-harmless: catalog data comes from the enricher, not from Sub2API's sync.
- Never write model metadata into Sub2API's DB (e.g. `extra.upstream_model_metadata` snapshots) — they go stale by construction; the intersection makes them unnecessary.
- Catalog visibility is the intersection of the enriched inventory, the group's configured models list, and Sub2API's account model-mapping union. Adding a group entry alone does not make an unmapped model visible. Listing a model is not proof that an inference request succeeds.
- Change account/group configuration through the supported admin API/UI while preserving unrelated settings; verify the served catalog afterward. Do not assume every credentials field is merged by a partial PUT, and do not diagnose stale cache or restart services merely because a model is absent. Follow the [coupled-service operations policy](operations.md#operations) if a restart is separately required.
- Troubleshoot catalog metadata via `http://127.0.0.1:9083/models-table` (or the Tailscale bind): missing capability cells show `未知`, while explicit nulls show `null`; enricher WARN logs name the failing channel `prefix`. The page's `POST /models-table/refresh` button bypasses the enricher's normal five-minute snapshot/read/projection caches, but it does **not** run or control the independent `cpa-model-sync` service, whose production interval is ten minutes. CPA must already have loaded a provider before the refresh can observe it. `proxy_max_temp_file_size 0` prevents concurrent large responses from exhausting the sidecar's small temporary filesystem.
- The front intersection validates identities and keeps selected records' original JSON fragments, avoiding Lua floating-point re-encoding of unknown numbers. Duplicate routing keys/collections fail closed. All external `/v1/models` and `/models` requests share one APISIX-wide admission slot across workers and callers; excess requests wait briefly, then receive bounded `503` instead of running concurrently. Entitlement-first ordering, final-entity ETags and 64 MiB limits remain in place; caching is confined to the enricher's upstream reads.
- Outbound pool slots remain held until response bodies close. Native/API-call, management inventory and bulk-source responses keep their respective 64/8/16 MiB limits; exceeding a limit is an error, not silent truncation.
- Independent output-token fields and three-column display: [local verification and compatibility](output-token-field-semantics-verification.md), [2026-09-08 production deployment](output-token-field-deployment-2026-09-08.md). The subsequent [five-channel source configuration deployment](source-chain-deployment-2026-09-08.md) records the current 78 output-field / 22 input-limit coverage snapshot.
- Pure server-rendered page implementation, browser-without-JS checks and deployment limits: [SSR verification](models-table-ssr-verification.md), [2026-09-08 production cutover](models-table-ssr-deployment-2026-09-08.md).
- Reproducible local checks and the 45-scenario evidence map: [layered metadata verification](layered-metadata-verification.md). This is implementation/fixture evidence, not a production deployment or inference claim.
- The enricher needs no egress policy: source data is bundled at build time, and channel-native endpoints (e.g. ollama.com `POST /api/show`) are reached by CPA through `api-call`, so CPA's egress policy must allow them; a denied read degrades that channel to a WARN, never a catalog failure.
- `/models-table` also lists models hidden by `include_models` with the deciding rule, and models kept only because another model references them (`inherit`/`metadata_from`); hidden, unreferenced models are not processed.
